# ADR-0001: 모듈러 모놀리스로 시작하고 M4에서 분리한다

## 상태

채택 (2026-08-18)

## 배경

주문과 결제를 다루는 시스템을 만든다. 시작 시점에 정할 것이 하나 있었다 —
**처음부터 서비스를 나눌 것인가, 한 덩어리로 만들 것인가.**

마이크로서비스로 시작하면 시작하자마자 분산 시스템의 문제를 전부 떠안는다.
서비스 간 호출 실패, 네트워크 지연, 분산 트랜잭션, 서비스별 배포 파이프라인.
아직 도메인 경계가 어디인지도 모르는 상태에서 그 비용을 내게 된다.

반대로 그냥 한 덩어리로 만들면 편하지만, 시간이 지나면 모든 코드가 모든 코드를 부른다.
나중에 나누려고 보면 이미 나눌 수 없는 상태다.

## 결정

**모듈러 모놀리스로 시작한다.** 하나의 프로세스로 배포하되, 내부는 처음부터
독립 배포 가능한 것처럼 나눠둔다. M4에서 실제로 물리 분리한다.

경계는 규칙으로 못 박고, 규칙을 어기면 **빌드가 깨지게** 만든다.

- `order`와 `payment`는 서로를 직접 참조하지 못한다 (Gradle 의존성 + ArchUnit)
- 모듈 간 통신은 이벤트로만 한다
- `@Transactional`이 모듈 경계를 넘지 못한다
- DB 스키마를 나누고 스키마 간 JOIN을 금지한다

## 대안

**(가) 처음부터 마이크로서비스**

버린 이유는 순서다. 도메인을 모르는 상태에서 그은 경계는 대부분 틀린다.
틀린 경계를 나중에 고치려면 서비스 간 데이터 이전이 필요한데, 이게 모놀리스에서
패키지를 옮기는 것보다 훨씬 비싸다.

**(나) 그냥 모놀리스, 나중에 필요하면 나눈다**

가장 흔한 선택이고 가장 흔하게 실패한다.
"나중에 나눈다"가 실제로 일어나려면 나눌 수 있는 상태여야 하는데,
규칙이 없으면 6개월 뒤에 그 상태가 아니다.

**핵심은 "나눌 수 있는 상태를 유지하는 비용"을 매일 조금씩 내느냐,
"나눌 수 없게 된 것을 되돌리는 비용"을 한 번에 크게 내느냐다.**
전자를 택했다.

**(다) 규칙을 문서로만 두기**

지켜지지 않는다. 급할 때 제일 먼저 무시되는 게 문서다.
그래서 ArchUnit 테스트로 만들었다 — 어기면 CI가 빨간불이 된다.

## 결과

**얻은 것**

- 도메인 경계가 틀렸다는 걸 알았을 때 패키지를 옮기는 것으로 고칠 수 있다
- 로컬 개발이 단순하다. 프로세스 하나만 띄우면 된다
- M4에서 분리할 때 "무엇을 떼어내야 하는지"가 이미 코드에 표시돼 있다

**포기한 것**

- **불편함을 자초했다.** 같은 프로세스 안에 있는데도 `order`가 `payment`를 직접 못 부른다.
  간단한 조회 하나도 이벤트나 별도 계약으로 돌아가야 한다
- 스키마를 나눴으니 JOIN 한 번이면 끝날 조회를 두 번 나눠서 한다
- ArchUnit 규칙 자체를 유지보수해야 한다. 규칙이 틀리면 정상 코드가 막힌다

**이 불편함이 설계의 목적이다.** 편하게 쓸 수 있으면 결국 그렇게 쓰게 되고,
그 순간 분리 가능성이 사라진다.
