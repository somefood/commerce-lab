# ADR-0002: 스키마 마이그레이션 도구로 Flyway를 쓴다

## 상태

채택 (2026-08-19)

## 배경

DB 테이블을 만들고 바꾸는 방법을 정해야 했다. 선택지가 크게 둘이었다.

JPA에는 `ddl-auto`라는 설정이 있다. 엔티티 클래스를 보고 하이버네이트가 테이블을
알아서 만들어준다. 개발 초기에 편하다 — 필드를 추가하면 컬럼이 따라 생긴다.

문제는 **실행되는 SQL이 어디에도 남지 않는다**는 것이다.
운영 DB에 무슨 DDL이 나갔는지 아무도 모르고, 코드 리뷰로 확인할 수도 없다.
"이 컬럼이 언제 왜 생겼나"를 물으면 답할 방법이 없다.

## 결정

**Flyway를 쓴다.** 마이그레이션 SQL을 파일로 레포에 남기고,
하이버네이트는 `ddl-auto: validate`로 **검사만** 한다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate   # 만들지 않는다. 엔티티와 테이블이 어긋나면 부팅이 실패한다
```

`validate`가 중요하다. 엔티티에 필드를 추가하고 마이그레이션을 안 쓰면
**첫 쿼리가 아니라 앱 부팅에서 실패한다.** 오타나 `@Table` 누락이 즉시 드러난다.

Flyway 이력 테이블(`flyway_schema_history`)은 `public` 스키마에 둔다.
`order` 스키마에 두면 M4에서 스키마를 떼어낼 때 이력까지 딸려간다.

## 대안

**(가) `ddl-auto: update`**

버린 이유는 셋이다.

1. 실행된 SQL이 기록에 안 남는다. 되돌릴 방법도, 리뷰할 방법도 없다
2. **컬럼을 지우지 않는다.** 필드를 삭제해도 컬럼은 남아서, 스키마가 조용히 쓰레기를 쌓는다
3. 하이버네이트 버전이 올라가면 생성되는 DDL이 달라질 수 있다.
   같은 코드가 환경에 따라 다른 테이블을 만든다

운영에서 쓰면 안 되는 설정으로 널리 알려져 있는데, 이유가 위 셋이다.

**(나) Liquibase**

Flyway와 경쟁 관계인 도구다. 기능은 더 많다 —
XML/YAML로 DB 독립적으로 쓸 수 있고, 롤백 스크립트를 자동 생성해준다.

버린 이유: **이 프로젝트는 Postgres에 고정이다.** DB 독립성을 쓸 일이 없는데
그걸 위한 추상 계층(XML 변경셋)을 배우고 유지해야 한다.
Flyway는 그냥 SQL 파일이라 배울 게 없고, DB 문법을 그대로 쓸 수 있다.

부분 인덱스나 `GENERATED ALWAYS AS IDENTITY` 같은 Postgres 고유 기능을 쓰는데,
추상 계층을 거치면 오히려 방해가 된다.

## 결과

**얻은 것**

- `V1__create_order_tables.sql`이 레포에 있다. 실행될 SQL을 리뷰할 수 있다
- 엔티티와 테이블이 어긋나면 부팅에서 실패한다. 런타임에 터지지 않는다
- 테이블 정의에 주석으로 근거를 남길 수 있다
  (실제로 "왜 available 컬럼을 두지 않는가"를 SQL 주석으로 적어뒀다)

**포기한 것**

- **편함.** 필드를 추가할 때마다 마이그레이션 파일을 직접 써야 한다
- 마이그레이션을 고치면 `docker compose down -v`로 DB를 날리고 다시 띄워야 한다.
  이미 적용된 파일을 수정하면 체크섬이 안 맞아 Flyway가 거부한다
- 되돌리기(rollback) 스크립트는 직접 쓴다. Flyway 무료판에는 없다

**겪은 사고 하나.** psql로 DDL을 직접 넣어봤다가 Flyway 이력과 어긋나서
`relation "products" already exists`로 앱이 안 떴다.
**Flyway를 쓰기로 했으면 DB 변경은 전부 Flyway로만 한다.** 예외를 두는 순간 이력이 거짓말이 된다.
