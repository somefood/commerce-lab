# ADR-0004: 선점 만료를 주기 배치 단독으로 구동한다

## 상태

채택 (2026-08-19)

## 배경

주문과 결제 사이에는 시간이 있다. 사용자가 카드를 꺼내고, PG가 승인하고,
은행이 응답하는 동안 재고를 어떻게 다룰지 정해야 했다.

바로 깎으면 결제 실패 시 되돌릴 근거가 없고, 결제 완료 후에 깎으면
이미 결제한 사용자에게 품절을 통보해야 한다. 그래서 **선점(reservation)** 을 쓴다 —
주문 시점에 "팔릴 예정"으로 잡아두고, 결제 완료 시 확정, 실패 시 반환.

여기서 문제가 생긴다. DB 락은 트랜잭션이 끝나면 자동으로 풀리지만,
**선점은 트랜잭션보다 오래 산다.** 사용자가 결제창을 닫고 사라지면
그 선점을 풀어줄 사람이 아무도 없다. 재고가 영원히 잠긴다.

누군가는 만료된 선점을 회수해야 한다. 그 "누군가"를 무엇으로 만들 것인가가 이 결정이다.

## 결정

**주기 배치 단독으로 간다.** Redis TTL 이벤트는 쓰지 않는다.

| 항목 | 값 | 이유 |
|---|---|---|
| TTL | 3분 | 카드 입력·인증에 넉넉하면서 재고를 너무 오래 묶지 않는 선 |
| 배치 주기 | 5초 | 만료 후 최대 5초 늦게 풀린다. 사람이 못 느끼는 지연 |
| 1회 처리량 | 500건 | 한 번에 다 처리하려다 트랜잭션이 길어지는 것을 막는다 |

**진실의 원천은 DB다.** `reservations.expires_at`이 지났으면 만료다.
Redis는 M1에서 아예 쓰지 않는다.

쿼리는 `WHERE status = 'HELD' AND expires_at <= now()`이고,
이걸 위해 부분 인덱스를 뒀다.

```sql
CREATE INDEX idx_reservations_expiring
    ON "order".reservations (expires_at) WHERE status = 'HELD';
```

확정·만료된 과거 예약은 이 쿼리의 대상이 아니다. 인덱스가 작을수록 갱신 비용도 작다.

## 대안

**(가) Redis TTL 이벤트 (keyspace notification)**

Redis에 키를 넣고 TTL을 걸면 만료 시점에 이벤트가 날아온다. 지연이 거의 없다.

버린 이유: **Redis의 만료 이벤트는 유실될 수 있다.**
구독자가 잠깐 끊긴 사이에 만료된 키의 이벤트는 다시 오지 않는다.
재고가 영원히 잠기는 사고가 정확히 그 순간에 생긴다.

그리고 진실의 원천이 둘이 된다. Redis에는 만료됐는데 DB에는 HELD로 남아 있으면
어느 쪽이 맞나? 이 질문에 답하려면 결국 DB를 확인해야 하고,
그러면 Redis는 "빠르게 알려주는 힌트"일 뿐 없어도 되는 것이 된다.

**(나) 배치 + Redis 힌트 병행**

Redis 이벤트로 빠르게 처리하고, 놓친 것은 배치가 줍는 구조다.
실무에서 흔한 절충안이고 지연이 짧다.

버린 이유는 **복잡도 대비 이득이 M1에서 없다는 것**이다.
5초 지연이 문제가 되는 시나리오가 아직 없는데,
두 경로가 같은 선점을 동시에 처리하는 경쟁 조건을 먼저 떠안게 된다.

필요해지면 나중에 얹을 수 있다. 지금 얹으면 뺄 수 없다.

**(다) 조회 시점에 만료 판정 (lazy expiration)**

배치를 아예 두지 않고, 재고를 조회할 때마다 `expires_at < now()`인 선점을 무시한다.

버린 이유: 만료된 선점이 DB에 HELD로 계속 쌓인다.
`inventories.reserved` 집계값도 어긋난 채로 남는다.
그리고 "아무도 조회하지 않는 상품"의 재고는 영원히 풀리지 않는다.

## 결과

**얻은 것**

- 만료 판정 로직이 한 곳에만 있다. 어긋날 곳이 없다
- Redis가 죽어도 만료가 동작한다. M1에서 Redis 의존이 아예 없다
- 배치가 멈추면 눈에 띈다 — 재고가 안 풀리는 게 바로 보인다

**포기한 것**

- **최대 5초 지연.** 재고가 만료됐는데 5초 동안 다음 사람이 못 산다
- 배치가 도는 동안 DB에 주기적인 부하가 있다. 5초마다 인덱스 스캔이 한 번씩 돈다
- **배치 자체가 단일 장애점이다.** 배치가 죽으면 아무도 모르게 재고가 계속 잠긴다.
  이걸 감시하는 것은 M5 관측성의 몫으로 미뤘다

**남은 어려운 문제.** 만료 배치가 선점을 풀려는 순간, 결제 완료 이벤트가 같은 선점을
확정하려 할 수 있다. 둘 다 성공하면 재고가 반환되면서 동시에 확정된다.
M1 3단계에서 이 경쟁을 다룬다 — 테스트 이름이
`만료 처리와 확정 처리는 서로를 배제한다`이다.
