# 이커머스 용어 사전

> 새 용어를 만날 때마다 여기에 추가한다. 면접 전 마지막으로 훑는 문서.

## 상품 (Catalog)

| 용어 | 뜻 |
|---|---|
| **카탈로그 (Catalog)** | 판매 가능한 상품 정보 전체. "카탈로그 팀"은 상품 정보를 다루는 팀 |
| **SKU (Stock Keeping Unit)** | 재고 관리의 최소 단위. "검정 티셔츠 M사이즈"와 "검정 티셔츠 L사이즈"는 같은 상품이지만 다른 SKU |
| **옵션 (Option/Variant)** | 색상, 사이즈처럼 하나의 상품 아래 갈라지는 변형. 옵션 조합 하나가 보통 SKU 하나가 됨 |
| **품절 (Sold Out) / 재입고 (Restock)** | 재고 0 상태 / 재고 보충. 재입고 알림은 이커머스 단골 기능 |
| **드롭 (Drop)** | 한정 수량 상품을 특정 시각에 오픈해 선착순 판매하는 방식 (나이키 SNKRS가 유명) |

## 주문 (Order)

| 용어 | 뜻 |
|---|---|
| **장바구니 (Cart)** | 구매 전 담아두는 임시 목록. 로그인 전/후 병합 처리가 은근히 까다로움 |
| **주문서 (Checkout)** | 장바구니 → 결제 사이의 단계. 배송지, 쿠폰, 최종 금액 확정이 여기서 일어남 |
| **주문 (Order)** | 구매 확정 요청. 이커머스에서 가장 복잡한 도메인 객체 |
| **주문 스냅샷** | 주문 시점의 상품명/가격을 주문에 **복사**해 저장하는 것. 이후 상품 가격이 바뀌어도 과거 주문은 그대로여야 하므로 |
| **주문 상태 머신** | 주문접수 → 결제완료 → 배송준비 → 배송중 → 배송완료 → 구매확정 등 정해진 상태 전이 규칙 |
| **애그리거트 (Aggregate)** | DDD 용어. 함께 일관성을 유지해야 하는 객체 묶음 (주문 + 주문항목). 트랜잭션의 단위 |

## 재고 (Inventory)

| 용어 | 뜻 |
|---|---|
| **재고 차감** | 주문/결제 시 재고를 줄이는 것. "언제 차감하느냐"(주문 시? 결제 시?)가 중요한 설계 결정 |
| **재고 선점 (Reservation)** | 결제 진행 동안 재고를 임시로 잡아두는 것. 시간 초과 시 해제 |
| **오버셀링 (Overselling)** | 재고보다 많이 팔리는 사고. 동시성 제어 실패의 대표 결과 |

## 결제 (Payment)

| 용어 | 뜻 |
|---|---|
| **PG (Payment Gateway)** | 결제 대행사 (토스페이먼츠, 나이스페이 등). 카드사와 쇼핑몰 사이의 중개자 |
| **결제 승인 (Approval)** | PG가 카드사에서 최종 승인을 받아내는 것. "승인 요청 → 승인 완료"가 핵심 플로우 |
| **웹훅 (Webhook)** | PG가 결제 결과를 우리 서버로 알려주는 역방향 HTTP 호출. 유실/중복 대비 필수 |
| **멱등성 (Idempotency)** | 같은 요청이 여러 번 와도 결과가 한 번 처리한 것과 같은 성질. 결제에서 목숨같이 중요 |
| **PG 위·변조 검증** | 클라이언트가 보낸 결제 금액을 믿지 않고 서버가 주문 금액과 대조하는 것 |
| **정산 (Settlement)** | PG가 판매 대금을 쇼핑몰에 입금해주는 것 (보통 D+2 등) |
| **에스크로 (Escrow)** | 구매 확정 전까지 대금을 제3자가 보관하는 제도 |

## 배송/CS

| 용어 | 뜻 |
|---|---|
| **풀필먼트 (Fulfillment)** | 주문 이후의 물류 전체 (피킹, 패킹, 배송) |
| **반품/교환/환불 (RMA)** | Return Merchandise Authorization. 역방향 물류 + 부분 환불 계산이 지옥으로 유명 |

## 지표 (Business)

| 용어 | 뜻 |
|---|---|
| **GMV (Gross Merchandise Value)** | 총 거래액. 이커머스 회사의 대표 규모 지표 |
| **전환율 (Conversion Rate)** | 방문자 중 구매까지 간 비율 |
| **객단가 (AOV)** | Average Order Value. 주문 1건당 평균 금액 |

## 인증/보안

| 용어 | 뜻 |
|---|---|
| **인증 (Authentication)** | "너 누구야?" 신원 확인. 실패 시 401 |
| **인가 (Authorization)** | "그거 해도 돼?" 권한 확인. 실패 시 403 |
| **JWT (JSON Web Token)** | 서명된 자기완결형 토큰. 서버가 상태를 안 가져도 검증 가능 → [학습 노트](learning/03-auth-primer.md) |
| **Bearer 토큰** | `Authorization: Bearer <token>` 헤더 형식. "이 토큰을 가진 자(bearer)를 인증한다" |
| **Claim** | JWT 페이로드의 각 항목 (`sub`, `exp`, `role` 등) |
| **BCrypt** | 의도적으로 느린 비밀번호 해시 알고리즘. 솔트 내장 |
| **Stateless** | 서버가 요청 간 상태(세션)를 보관하지 않음. 수평 확장의 전제 |
| **CSRF** | 브라우저가 쿠키를 자동 전송하는 성질을 악용한 공격. 헤더 토큰 방식에선 해당 없음 |
| **계정 열거 공격** | "없는 이메일"/"틀린 비밀번호" 응답 차이로 가입 여부를 알아내는 공격. 같은 메시지로 방어 |
| **Refresh Token** | 짧은 Access Token을 재발급받기 위한 긴 수명 토큰. 즉시 무효화 문제의 현실적 타협 |

## 기술 (이 프로젝트에서 만나게 될 것들)

| 용어 | 뜻 | 등장 Phase |
|---|---|---|
| **Lost Update (갱신 유실)** | 두 주체가 읽고-수정하고-쓸 때 나중 쓰기가 먼저 쓰기를 지워버리는 현상 → [학습 노트](learning/01-lost-update.md) | 1 (경험함) |
| **낙관적 락 / 비관적 락** | 동시 수정 충돌을 "버전 검사로 사후 감지" / "선점 잠금으로 사전 차단" | 5 |
| **분산 락** | 여러 서버가 하나의 자원을 두고 경쟁할 때 Redis 등으로 잠그는 것 | 5 |
| **Transactional Outbox** | DB 트랜잭션과 이벤트 발행을 원자적으로 묶는 패턴 (이벤트 유실 방지) | 6 |
| **Saga / 보상 트랜잭션** | 서비스가 분리되어 하나의 트랜잭션으로 못 묶을 때, 실패 시 되돌리는 작업을 명시적으로 수행 | 8 |
