# Lost Update (갱신 유실)

> Phase 1에서 실제로 겪은 문제. 원본 코드: PUT `/api/products/{id}`가 `stockQuantity`를 통째로 덮어쓰던 시절.

## 정의

두 주체가 같은 데이터를 "읽고 → 수정하고 → 저장"할 때, **나중에 저장한 쪽이 먼저 저장한 쪽의 변경을 소리 없이 지워버리는** 현상. 에러도 안 나고 로그도 안 남는다 — 그래서 무섭다.

## 우리가 겪은 시나리오

```
14:00:00.000  현재 재고 10개
14:00:00.100  관리자가 상품 수정 화면을 연다 (화면에 재고 10 표시)  ← 읽기
14:00:01.000  고객이 3개 주문 → 재고 7개로 차감됨
14:00:05.000  관리자가 상품명만 고치고 저장
              → PUT {"name":"새 이름", ..., "stockQuantity":10}    ← 쓰기 (5초 전에 읽은 값!)

결과:   재고 10개 (고객의 차감이 유실됨)
정답:   재고 7개
사고:   유령 재고 3개 → 없는 재고를 판매 → 오버셀링
```

핵심 패턴: **read-modify-write 사이의 시간 틈**. 읽기와 쓰기 사이에 다른 주체가 끼어들 수 있는 데이터라면, 그 틈이 0.001초든 5초든 사고는 난다.

## 원칙

> **"읽은 값을 갖고 있다가 다시 쓰는 데이터는, 그 사이에 다른 주체가 바꿀 수 있다면 덮어쓰기 금지."**

판별법: "이 필드를 동시에 바꾸는 주체가 둘 이상인가?"
- 상품명, 설명: 관리자만 바꿈 → 덮어쓰기 허용
- 재고: 고객 주문(차감) + 관리자 입고(증가)가 **경쟁** → 덮어쓰기 금지

## 해결 스펙트럼 (약한 것 → 강한 것)

### 1. API 설계로 예방 — 우리가 Phase 1에서 한 것 ✅

- 경쟁 자원(재고)을 일반 수정 API에서 **분리**: `PUT /products/{id}`에서 stockQuantity 제거
- 절대값 덮어쓰기 대신 **증감(델타)**: `POST /products/{id}/stock` + `{"quantity": -3}`
- "재고를 10으로 만들어라"(상태 덮어쓰기)가 아니라 "3개 차감이라는 **사건**을 반영해라"

### 2. 원자적 UPDATE 쿼리

애플리케이션에서 읽고 계산하지 않고, DB가 한 방에 처리:

```sql
UPDATE product
SET stock_quantity = stock_quantity - 3
WHERE id = 1 AND stock_quantity >= 3;   -- 영향받은 행이 0이면 재고 부족
```

read-modify-write 자체가 사라지므로 틈이 없다. 단순하고 강력하지만, 도메인 로직이 SQL로 새어나가는 트레이드오프.

### 3. 낙관적 락 (Optimistic Lock) — Phase 5에서 실습

- 엔티티에 `@Version` 컬럼을 두고, 저장 시 "내가 읽었을 때의 버전 그대로인가?"를 검사
- 다른 누군가 먼저 바꿨으면 버전이 달라져서 **저장이 실패** (OptimisticLockException) → 재시도 or 사용자에게 알림
- "충돌은 드물 것"이라고 낙관하고, 충돌 시 사후에 감지. 잠금이 없어 성능 좋음

### 4. 비관적 락 (Pessimistic Lock) — Phase 5에서 실습

- 읽는 순간부터 잠근다: `SELECT ... FOR UPDATE`
- 내가 끝날 때까지 다른 트랜잭션은 대기. "충돌이 잦을 것"이라고 비관하고 사전 차단
- 확실하지만 대기·데드락 비용. 한정판 드롭처럼 경쟁이 극심한 곳에서 고려

### 5. 분산 락 / 원자적 카운터 (Redis) — Phase 5에서 실습

- 서버가 여러 대가 되면 DB 락만으로 부족한 경우가 생긴다 → Redis 등 외부 저장소로 잠금/카운팅

## 주의: 증감 방식도 만능이 아니다

증감 API로 바꿔도 코드가 "현재 값을 **읽고** → 더하고 → 저장"(우리의 현재 구현!)이라면, 두 요청이 동시에 같은 값을 읽는 순간 여전히 유실된다. 지금은 요청이 드물어 괜찮지만, Phase 5에서 부하 테스트(k6)로 이 문제를 **눈으로 확인**하고 락으로 해결할 예정.

## 면접 예상 질문

**Q. 동시성 문제를 겪거나 고민해본 적 있나요?**
→ 위 시나리오를 그대로 말하면 된다: PUT이 재고를 덮어쓰는 설계였다 → Lost Update로 유령 재고 발생 가능 → ① 재고를 별도 증감 API로 분리해 설계 차원에서 방어 ② 근본적으로는 낙관적/비관적 락으로 해결하며 트레이드오프는 충돌 빈도에 따라 선택.

**Q. 낙관적 락 vs 비관적 락, 언제 뭘 쓰나요?**
→ 충돌이 드물면 낙관적(잠금 비용 없음, 실패 시 재시도), 충돌이 잦고 재시도 비용이 크면 비관적(대기 비용 감수). 예: 게시글 수정은 낙관적, 한정판 재고 차감은 비관적/원자적 연산 계열.
