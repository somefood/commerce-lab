# 인증 보안 3문 3답 — 계정 열거, JWT 로그아웃, 만료시간

> Phase 2 마감 리뷰 질문 3개에 대한 내 답변과 팀장 피드백 정리 (2026-09-01).
> 형식: 내 답변의 핵심 → 맞았던 것 → 보강할 것. 면접 직전에 이 문서만 읽어도 복원 가능하게.

## Q1. 로그인 실패 시 "없는 이메일"과 "틀린 비밀번호"를 구분해서 알려주면 안 되는 이유는?

### 내 답변 핵심
구분해서 알려주면 공격자에게 추측 근거를 준다 — "이메일은 맞았으니 비밀번호만 브루트포스하면 된다" /
"없는 이메일이니 다른 걸 돌려보자". 최대한 노출하지 않는 게 맞다. 단, 서버 내부 로그에는 세세하게 구분 기록.

### 맞았던 것
- 핵심 원리 정확: **응답 차이 = 공격자의 정보**. 그래서 우리 구현도 두 경우 모두
  `InvalidAuthenticationException("이메일 또는 비밀번호가 올바르지 않습니다.")` 하나로 통일했다.
- "로그엔 세세히"는 실무 필수 디테일 — CS 대응("로그인이 안 돼요")과 공격 탐지(특정 IP가 없는 이메일만 수천 번)를 위해
  서버는 진실을 알아야 한다. **사용자 응답과 내부 기록의 정보량은 다르게 설계한다.**

### 보강할 것
1. **메시지 통일은 로그인만의 문제가 아니다.** 우리 가입 API는 중복 이메일에 409를 돌려준다 —
   공격자는 로그인 대신 **가입 API로 이메일 존재를 확인**할 수 있다. 시스템 전체의 응답 일관성 문제.
   실무에선 가입 쪽은 UX 때문에 노출을 감수(+rate limiting으로 완화)하거나,
   완전히 막으려면 "입력하신 주소로 메일을 보냈습니다"(존재 여부 무관 동일 응답 + 이메일 인증) 방식으로 간다.
2. **타이밍 부채널**: 메시지를 통일해도 응답 시간이 다르다. 없는 이메일이면 BCrypt 비교(수십~수백ms)를
   건너뛰어 빨리 끝난다. 정밀 측정하면 가입 여부를 알 수 있다.
   방어: 회원이 없어도 더미 해시에 대고 `verify()`를 한 번 돌려 시간을 맞춘다.
3. **역할 구분**: 메시지 통일은 *정찰*을 막는 것. 브루트포스 *공격 자체*를 막는 건
   **rate limiting / 계정 잠금 / CAPTCHA**다. 층이 다른 방어를 섞어 말하지 않기.

## Q2. JWT는 서버가 상태를 안 가지는데, 로그아웃은 어떻게 구현하나?

### 내 답변 핵심
클라이언트가 토큰을 지워도 토큰 수명이 다한 건 아니라서 애매하다. 액세스 토큰을 짧게 가져가서
탈취돼도 오래 못 쓰게 하고, DB의 리프레시 토큰이 유효하면 자동 연장. 수평 스케일링 때문에 세션보다 JWT.

### 맞았던 것
- "클라이언트 삭제 ≠ 무효화" 인식 정확 — 서명이 유효한 토큰은 만료까지 살아 있다.
- **짧은 액세스 + 폐기 가능한(DB) 리프레시** = 업계 표준 타협안을 정확히 짚음.

### 보강할 것
1. **하이브리드라는 자각**: 리프레시 토큰을 DB에 두는 순간 상태(state)가 돌아온 것이다.
   실무 시스템은 거의 전부 "stateless 액세스 + stateful 리프레시" **하이브리드**다.
   "JWT는 stateless"를 순수하게 유지하는 시스템은 로그아웃 요구사항 앞에서 드물다 — 이 아이러니를 아는 게 강한 답변.
2. **즉시 무효화가 꼭 필요할 때** (강제 로그아웃, 계정 정지, 탈취 확인): **블랙리스트** —
   토큰 식별자(jti)를 남은 만료 시간 동안만 Redis에 보관. 무효화된 소수만 저장하므로 전체 세션 보관보다 훨씬 가볍다.
3. **리프레시 토큰 로테이션**: 갱신 때마다 리프레시도 재발급 + 이전 것 폐기.
   폐기된 리프레시로 갱신 시도가 오면 = 탈취 신호 → 해당 사용자 전체 세션 무효화. 현재 표준 관행.
4. **세션 vs JWT, 면접용 정밀 표현**: "세션은 수평 확장이 안 된다"는 틀린 말 (Redis 세션 스토어로 된다).
   정확한 차별점은 **검증 시 저장소 조회 횟수** — 세션은 요청마다 조회 1회, JWT는 0회(서명 검증만).
   "확장은 양쪽 다 되지만 요청당 비용 구조가 다르다"고 말하면 반박당하지 않는다.

## Q3. 액세스 토큰 10분 vs 24시간 — 각각 무엇을 얻고 잃나?

### 내 답변 핵심
10분: 보안↑, 재인증 왕복↑. 24시간: 왕복↓, 탈취 시 노출 시간이 너무 길다.
짧게 가는 게 낫다 — 그 정도 부하는 요즘 서버가 감당한다.

### 맞았던 것
- 트레이드오프 축(노출 시간 vs 갱신 비용) 정확, "짧게" 결론도 실무 다수파와 동일.

### 보강할 것
1. **짧은 만료의 진짜 비용은 서버 부하가 아니라 UX다.**
   리프레시 토큰이 **없으면**: 10분마다 사용자가 아이디/비밀번호를 다시 입력 → 사용자가 못 버틴다.
   리프레시가 **있으면**: 재발급은 백그라운드 API 호출 1번, 사용자는 인지 못 한다.
2. 따라서 **Q2와 Q3는 한 세트의 설계다** — 리프레시 토큰의 존재가 액세스 만료시간의 선택지를 바꾼다.
   "액세스는 공격 노출 시간만 보고 짧게, 편의는 리프레시가 책임진다"가 결론의 완전한 형태.
3. **실무 관례 수치** (면접에서 숫자를 말하면 신뢰가 올라간다):
   액세스 15분~1시간 (우리는 1시간), 리프레시 2주~1달.

## 우리 코드와의 연결

| 개념 | 구현 위치 |
|---|---|
| 단일 실패 메시지 | `InvalidAuthenticationException` (member/domain) |
| 실패 → 401 번역 | `GlobalExceptionHandler.handleInvalidAuthentication` |
| 액세스 만료 1시간 | `JwtTokenIssuer.EXPIRES_IN_SECONDS` |
| 가입 409 (열거 구멍, 감수한 트레이드오프) | `DuplicateEmailException` → 409 |
| 리프레시 토큰 | 미구현 — 배포 전 필요 시 도입 검토 (CURRICULUM 참조) |

## 면접 예상 질문

**Q. 로그인 실패 응답을 어떻게 설계하나요?**
→ 이메일 부재/비밀번호 불일치를 같은 메시지·같은 상태코드(401)로 통일 (계정 열거 방어).
서버 로그에는 구분 기록. 타이밍 차이까지 막으려면 더미 해시 비교. 브루트포스 자체는 rate limiting이 담당.

**Q. JWT 로그아웃은 어떻게 구현하나요?**
→ 완전한 stateless론 불가. 짧은 액세스 + DB 리프레시(폐기 가능) 하이브리드가 표준.
즉시 무효화 요건은 jti 블랙리스트(Redis, 만료까지만). 리프레시 로테이션으로 탈취 탐지.

**Q. 토큰 만료시간은 어떻게 정하나요?**
→ 액세스는 탈취 시 노출 허용 시간 기준으로 짧게(15분~1시간), UX는 리프레시 토큰이 책임.
만료시간 논의는 리프레시 전략과 분리해서 답할 수 없다.
