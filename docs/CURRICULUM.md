# 커리큘럼 — CRUD에서 서비스 분리까지

각 Phase는 **"과제 → 구현 → 코드 리뷰 → 리팩토링"** 사이클로 진행한다.
팀장(Claude)이 과제와 수용 기준을 제시하고, 구현이 끝나면 실무 스타일로 리뷰한다.

## 로드맵

### Phase 0 — 온보딩 ✅ (진행 중)
- 개발 환경 확인 (JDK 21, Docker, IntelliJ)
- 프로젝트 뼈대 이해: 멀티모듈이 왜 이렇게 나뉘어 있는지
- 첫 빌드 & 앱 실행 성공
- **산출물**: `./gradlew build` 그린, 첫 커밋

### Phase 1 — 상품(Product) CRUD × 헥사고날
- 헥사고날 아키텍처를 CRUD라는 익숙한 문제로 체득
- Kotlin 기본기: data class, null safety, 확장 함수
- REST API 설계, JPA 매핑, 계층별 테스트
- **핵심 질문**: "왜 컨트롤러가 서비스 구현체가 아니라 인터페이스(port)에 의존하는가?"

### Phase 2 — 회원 & 인증
- 회원가입/로그인, Spring Security + JWT
- 비밀번호 해싱, 토큰 만료/갱신 전략
- **핵심 질문**: "세션 대신 JWT를 쓰는 트레이드오프는?"

### Phase 3 — 장바구니 & 주문 + PostgreSQL 전환
- 도메인 모델링의 본격 시작: 주문은 이커머스에서 가장 복잡한 애그리거트
- 주문 상태 머신 (주문접수 → 결제대기 → 결제완료 → 배송 → 구매확정)
- 재고 차감과 트랜잭션 경계
- H2 → PostgreSQL (Docker), Flyway 마이그레이션 도입
- **핵심 질문**: "주문 생성 시점에 가격을 복사해서 저장하는 이유는?"

### Phase 3.5 — 1차 배포 🚀
- Docker 이미지 빌드, 미니 PC 배포, 도메인 연결 + HTTPS
- "일단 배포하고 계속 배포한다" — 이후 Phase는 전부 실서버에 반영
- **핵심 질문**: "로컬에선 되는데 서버에서 안 되는 이유 Top 3는?"

### Phase 4 — 결제
- 토스페이먼츠 테스트 연동 (실제 PG 연동 플로우 경험)
- 결제 승인/실패/취소, 웹훅 처리, **멱등성**(같은 요청이 두 번 와도 안전하게)
- 금액 검증: 클라이언트가 보낸 금액을 절대 믿지 않는다
- **핵심 질문**: "결제 승인 API 호출 직후 서버가 죽으면 어떻게 되는가?"

### Phase 5 — 한정판 드롭 (동시성)
- 선착순 재고 차감: 낙관적 락 vs 비관적 락 실측 비교
- Redis 도입: 캐시 + 원자적 재고 카운터
- 부하 테스트로 눈으로 확인 (k6)
- **핵심 질문**: "재고 100개에 1,000명이 동시에 주문하면 어떤 일이 벌어지는가?"

### Phase 6 — 이벤트 기반 모듈 통신
- 모듈 간 직접 호출 → 도메인 이벤트 발행/구독으로 전환
- Transactional Outbox 패턴 (이벤트 유실 방지)
- **핵심 질문**: "주문 모듈이 결제 모듈을 직접 호출하면 무엇이 문제인가?"

### Phase 7 — 운영 고도화
- CI/CD (GitHub Actions), 모니터링 (Actuator + Prometheus + Grafana)
- 구조화된 로깅, 장애 대응 시나리오
- **핵심 질문**: "배포했는데 에러율이 올라간다. 무엇부터 보는가?"

### Phase 8 — 결제 서비스 분리 (MSA 맛보기)
- 결제 모듈을 별도 서비스로 추출 — 모듈 경계를 잘 그어둔 덕을 보는 순간
- 서비스 간 HTTP 통신, 분산 트랜잭션 문제와 보상 트랜잭션(Saga)의 기초
- **핵심 질문**: "모놀리스에서 그냥 @Transactional이던 것이 분리 후엔 왜 문제가 되는가?"
